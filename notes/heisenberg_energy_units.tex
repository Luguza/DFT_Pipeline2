supercell sizes}
\author{Luca Frey}

\section*{TL;DR}

\code{HeisenbergMapper} only returns correct exchange constants when
\textbf{every input ordering has the same number of magnetic ions} (same
supercell size). Feed it orderings of mixed sizes and it returns
plausible-looking but wrong \code{J\_ij} --- \textbf{no exception, no warning}.

Mixed sizes are not an edge case: \code{MagneticStructureEnumerator} (the engine
behind atomate2's \code{MagneticOrderingsMaker}) produces them \emph{by default},
and the atomate2 exchange flow feeds all of them straight into
\code{HeisenbergMapper}. So the default path is the broken path.

There are \textbf{two independent bugs}; either one alone corrupts the result.
Both are fixed in \code{heisenberg.py} (see Sec.~\ref{sec:fix}).

\section{How the solve works (just enough to see the bugs)}
\label{sec:how}

Inputs: a list of magnetic structures (each with a \code{magmom} site property)
and their total DFT energies $E_k^{\mathrm{tot}}$ (eV, whole supercell of ordering
$k$).

\begin{enumerate}
\item \textbf{Normalise} --- \code{HeisenbergScreener.\_do\_cleanup} strips each
structure to its magnetic sublattice and divides energy by the
\textbf{magnetic-ion count}:
\[
  \varepsilon_k = E_k^{\mathrm{tot}} / N_k^{\mathrm{mag}}
  \qquad\text{(eV per magnetic ion --- intensive).}
\]

\item \textbf{Build the design matrix} (\code{\_get\_exchange\_df}) --- one row
per ordering: an \code{E} column $=\varepsilon_k$, an \code{E0} column $=1$, and
one \textbf{coupling column} per neighbour class,
\[
  C_{ab,k} = -\!\!\sum_{\langle i,j\rangle\in ab}\!\! s_i\,s_j
  \qquad\text{(summed over \emph{all} bonds in the cell).}
\]
This sum is \textbf{extensive} --- it scales with the supercell size. So each row
is $\varepsilon_k = E_0\cdot 1 + \sum_{ab} J_{ab}\,C_{ab,k}$.

\item \textbf{Solve} (\code{get\_exchange}) --- the matrix is forced
\textbf{square} (rows truncated to the number of unknowns) and solved by a
\textbf{direct inverse}:
\begin{lstlisting}
ex_mat = ex_mat[: ex_mat.shape[1] - 1]   # drop extra rows
H_inv  = np.linalg.inv(H)
j_ij   = H_inv @ E
\end{lstlisting}
It is \emph{not} a least-squares fit --- extra orderings are discarded, not used
to over-determine anything.
\end{enumerate}

The whole problem is the mismatch between steps 1 and 2: \textbf{the left-hand
side is per-ion (intensive), the coupling columns are per-cell (extensive).}

\section{Bug 1 --- normalisation mismatch makes the system ill-posed}
\label{sec:bug1}

Write ordering $k$'s supercell as $n_k$ primitive cells. Everything extensive
scales with $n_k$:
\[
  N_k^{\mathrm{mag}} = \nu\,n_k \quad(\nu=\text{mag ions / primitive cell}),
  \qquad
  C_{ab,k} = n_k\,c_{ab,k}.
\]
The energy we fit is intensive (divided by $N_k^{\mathrm{mag}}$), so it does
\textbf{not} depend on $n_k$. But the coupling columns still carry the $n_k$
factor. Matching the two sides forces
\[
  J_{ab}^{\text{(fitted)}} = J_{ab}^{\text{(physical)}} / N_k^{\mathrm{mag}},
\]
which is a single consistent value across all rows \textbf{only if
$N_k^{\mathrm{mag}}$ is the same for every ordering}. Mix the sizes and no single
$J$ set satisfies all rows --- the (still invertible) matrix returns garbage.

\paragraph{Fix.} Divide each coupling row by its own site count so the columns
become intensive too: \code{ex\_row[j\_columns] /= len(sgraph.structure)}. Then
the $n_k$ factor cancels on both sides and any mix of sizes is consistent.

\section{Bug 2 --- site labels are built from only the first structure}
\label{sec:bug2}

\code{unique\_site\_ids} (the map from site index $\to$ coupling-column id) is
built \textbf{once} from \code{ordered\_structures[0]}:
\begin{lstlisting}
self.unique_site_ids, self.wyckoff_ids = self._get_unique_sites(ordered_structures[0])
\end{lstlisting}
The orderings are sorted by energy first, so the lowest-energy ordering --- often
the \textbf{smallest cell} --- ends up at index 0. Its site map then only knows
the site indices that exist in that small cell. In larger cells, any unknown site
index is mapped to \code{None}, and \textbf{every bond touching such a site is
silently dropped} from the design matrix. Bigger cells lose most or all of their
bonds.

\paragraph{Fix.} Build one site map \emph{per ordering}, all anchored to a common
parent cell, so the same crystallographic orbit gets the same column id in every
ordering regardless of supercell size: \code{\_get\_unique\_sites(structures)}
plus \code{StructureMatcher(attempt\_supercell=True).get\_s2\_like\_s1(...)}.

\section{Why this is the default path, not an edge case}
\label{sec:trigger}

\code{MagneticStructureEnumerator} keeps the FM ordering at the
\textbf{primitive} cell but enumerates AFM/ferrimagnetic orderings over
supercells up to
\[
  \texttt{max\_cell\_size} = \max\!\big(1,\ \lfloor 4/N_{\mathrm{mag,prim}}\rfloor\big)
  \qquad(\code{analyzer.py}),
\]
so for a single magnetic site per primitive cell that's cells of 1--4 formula
units \emph{at once}. The atomate2 \code{ExchangeMaker.make\_from\_ordering\_doc}
then passes \textbf{all} of them to \code{HeisenbergMapper}, sorted by energy,
with no size filtering. A normal run therefore hands the mapper exactly the
mixed-size input that triggers both bugs.

\section{Fix summary}
\label{sec:fix}

Both fixes are in \code{heisenberg.py}:
\begin{enumerate}
\item \textbf{Bug 1:} normalise each coupling row by its site count
(\code{ex\_row[j\_columns] /= len(sgraph.structure)}) so the columns are per-ion
like the energies.
\item \textbf{Bug 2:} build a per-ordering \code{unique\_site\_ids} anchored to a
common parent cell via \code{StructureMatcher}, instead of reusing
\code{ordered\_structures[0]}'s map.
\end{enumerate}
With both applied, mixed supercell sizes fit consistently and the worked example
recovers $J_{\mathrm{nn}}=+12$, $J_{\mathrm{nnn}}=-4$~meV (per primitive cell)
regardless of which cell each ordering is given in.
